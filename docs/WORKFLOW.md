## 2. バックテスト実行フロー（詳細）

```
1. ユーザーが基準日を入力
2. 「実行」ボタン押下
3. システム:
   a. tickersテーブルから全銘柄取得
   b. 各ルール（rules/*.py）を動的ロード
   c. 各銘柄 × 各ルール でスコア計算:
      - need_financials() が True なら financials テーブル参照
      - 株価データは prices テーブルから取得
      - センチメントスコアは indicators テーブルから取得
   d. ルールごとにスコア降順ソート
   e. 総合ランキングは全ルールスコア合計でTOP10
   f. 結果を backtest_results テーブルに保存
4. UIが結果をタブごとに表示
```

## 3. データ蓄積フロー（財務データ）

```
初回実行:
  yfinance または edinet から直近4年分の財務データ取得
  → financials テーブルに INSERT

2回目実行（例: 1年後）:
  yfinance/edinet から現時点の直近4年分取得
  → すでにDBにある fiscal_year はスキップ（UPSERT）
  → 新しい fiscal_year のみ INSERT
  → DBには合計5年分（初回4年＋新規1年）が保持される

この仕組みにより、システムを運用し続けるほど
過去の財務データが蓄積され、長期バックテストの精度が向上する。
```

## 4. センチメントDLフロー

```
1. sentiment_download_log テーブルを参照
2. last_downloaded_at が NULL（未DL）または最も古い銘柄から N件 選択
3. 各銘柄:
   a. NewsAPI/Finnhub からニュース取得
   b. FinBERT でセンチメント分析
   c. 結果を indicators テーブルに保存
   d. sentiment_download_log を更新
4. 次回実行時は、続きの銘柄から再開

※ API制限に応じて N を調整可能（デフォルト: 50銘柄/回）
```

## 5. 新ルール追加フロー

```
1. rules/ 配下に新しい .py ファイルを作成
2. BaseRule を継承し、calculate() を実装
3. app.py 起動時に rules/ を自動スキャン
4. タブが自動追加され、バックテスト対象に含まれる

※ 再起動不要（Streamlitのホットリロード機能による）
```

## 6. エラーハンドリングフロー

```
ダウンロード中:
  - 特定銘柄でエラー → スキップ + error_log テーブルに記録
  - ネットワークエラー → 3回リトライ後、諦める
  - API制限 → 60秒待機してリトライ

バックテスト中:
  - データ不足（上場前）→ スコア0（評価対象外）
  - 財務データ不足 → need_financials=False のルールのみ評価
```
